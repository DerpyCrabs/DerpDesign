# Ladybird integration and bug triage

DerpDesign links an external worker to pristine upstream Ladybird commit `197c851802f23cf956800d8dfe5083e18a424490`. `scripts/setup-ladybird` verifies the downloaded archive and compares the source tree. Rendering uses upstream LibWebView/WebContent; the worker supplies the event loop, viewport/DPR, input translation, bitmap transport, popup composition and read-only inspection. Those adapter responsibilities can cause defects independently of upstream.

Do not classify every difference from Chromium as a Ladybird bug. First reproduce the same reduced page with the standalone upstream binary, matching viewport, DPR, fonts, theme, focus and input. Check a current upstream build before reporting a pinned-revision issue. Keep local harness mocks/build transforms out of the reduction unless they are essential to reproduce the web-platform behavior.

Current MCP tools expose project/demo/viewport/conditions, engine commit and capabilities, captures with source fingerprints, DOM trees, geometry, computed styles, readable author CSS rules and typed input. AI can use this evidence and local source access to build many layout reproductions. This is not complete DevTools parity: console history, network requests/responses, performance traces, full stylesheet source mapping, shadow-root inspection are missing. Point picking descends through same-origin frames and returns a `framePath` array for subsequent selector inspection; cross-origin frames remain unsupported. Ladybird rule matching is CSSOM-based; unreadable stylesheets and unsupported rule groups are reported explicitly. UA rules and pseudo-element styles are not comprehensively represented.

A reliable report includes one concrete failure, minimal HTML/CSS/JS/assets, exact upstream revision and environment, steps/expected/actual, and screenshots from the standalone browser. The screenshot alone does not establish root cause. Ladybird requests one issue per bug: https://github.com/LadybirdBrowser/ladybird/blob/master/CONTRIBUTING.md .

Worker groups receive cleanup on normal shutdown and worker failure; the Ladybird worker terminates its owned group when its parent dies. The abrupt-host-loss test freezes a real renderer before killing the host and requires every owned descendant to disappear.

The iframe-removal regression exposed a detached console evaluation context. Inspection now uses upstream's current-top-document `run_javascript` API with a fixed read-only program and tagged result transport. `python3 tests/ladybird/iframe-removal.py` verifies parent close, focused-child close, and child-requested close, with subsequent inspection, input and PNG capture. The transport's duplicate stderr records are filtered locally; ordinary console output and errors remain. No upstream source patch is required for this adapter fix. Hover requests use `geometryOnly` to avoid collecting full DOM and CSS on every pointer move. Renderer crash state remains sticky across automatic error-page navigation, until an explicit reset.

The standalone SharedWorker lifetime diagnostic is described in `tests/ladybird/shared-worker-removal.md`. It is an exploratory reduction, not a confirmed upstream crash reproduction.

Validation also covers known-crash input/resize: they return `engine_crashed` immediately rather than waiting for an input acknowledgement that cannot arrive. Reset reloads the original scenario URL and is tested with recovered DOM and rendered pixels. Same-origin point selection, frame-relative tree selection and lightweight hover geometry are exercised through native Qt on generic fixtures at 160% display scale.
